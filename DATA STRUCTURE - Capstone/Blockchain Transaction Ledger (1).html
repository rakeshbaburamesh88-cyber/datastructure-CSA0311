Why a blockchain ledger?

A ledger kept as ordinary records can be edited silently, and one changed entry is hard to notice. We need a ledger where any change is detectable, cheap to verify, and costly to rewrite.

Module 1: Linked list

Node: index, timestamp, transactions, Merkle root, nonce, its hash and a link to the previous block.

Append: O(1) with a tail pointer, no traversal.

Validate: walk from genesis and check every link in O(n).

Module 2: Merkle tree

Leaves are SHA-256 hashes of transactions. Parents hash their two children, and the root sits in the block header.

Module 3: Hash and PoW

Editing one transaction changes the Merkle root, then the block hash, then breaks every later link. Mining loops over nonces until the hash meets the target.

End-to-end transaction workflow

  1. Submit

    A transaction (sender, receiver, amount) enters the pending pool.

  2. Hash and index

    Each transaction is hashed and stored in the hash table.

  3. Build Merkle root

    Hashes are paired upward until a single root remains.

  4. Assemble block

    The header gets the Merkle root and the previous block’s hash.

  5. Mine

    Increment the nonce until the block hash meets the difficulty target.

  6. Append and validate

    Attach the block to the chain, then re-verify the links.

Questions the project answers

Why does editing one transaction break the whole chain?

The edit changes that transaction’s leaf hash, then its parents, then the Merkle root in the header. The block hash changes, so the next block’s stored previous hash no longer matches, and the mismatch carries on down the chain.

Why keep a tail pointer?

Without it, adding a block means walking from the genesis block, which costs O(n). The tail pointer always references the last block, so the new one attaches in constant time.

Why a Merkle tree instead of one big hash?

A single hash of every transaction proves nothing about one transaction unless you hold all of them. In a tree, a verifier needs only the sibling hashes along one path, which is O(log n).

What does the hash table add?

It indexes blocks and transactions by hash, so a stored hash and a recomputed one are compared in O(1) on average instead of scanning the chain.

Why is rewriting history expensive?

Changing block k means mining block k again and every block after it, each needing about 2d hashes. An honest append mines only once.

Conclusion
